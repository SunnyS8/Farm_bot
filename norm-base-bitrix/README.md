# Нормативная база в коробочном Bitrix24 — первый вертикальный срез

**Статус:** исходный код, не установлен на crm.escom.group. Портал, Farma BI, бот и корпус не изменены. Внешние запросы ИИ при разработке не выполнялись.

## Что реализовано

- Русский интерфейс: документы, оригиналы, история редакций, проверенные пункты и консультант.
- Авторизация через ядро Bitrix на том же HTTPS origin, проверка внутреннего сотрудника; настройка групп чтения. Администрирование — исключительно `$USER->IsAdmin()` на сервере.
- Загрузка PDF, DOC, DOCX, HTML; allowlist, сигнатуры, случайные внутренние имена, ограничение размера, SHA-256. HTML отображается только как обычный текст; оригиналы выдаются исключительно вложением через защищённый обработчик.
- Оригиналы неизменяемы. Новая загрузка создаёт новую редакцию. Публикация выполняется один раз после ручной сверки: источник, дата проверки, срок редакции, точный текст/локатор и отдельные сроки каждого пункта. События upload/review записываются в аудит.
- Только проверенные фрагменты с подходящими датами допускаются к ИИ. Пересекающиеся действующие редакции одного документа исключаются, а не выбираются по времени загрузки.
- Ограниченный лексический поиск (до 500 действующих фрагментов; при превышении отказ), максимум 6 фрагментов в запросе Hubris. Результат — только дословные цитаты, подтверждённые подстрокой в сохранённом тексте, с локатором, датами и ссылкой на защищённый оригинал. Непроверенная генерация юридического заключения сознательно не показывается.

## Архитектура

```text
Bitrix same-origin iframe → index.php / assets
                         → api.php → core session / CSRF / admin guard
                                   → Application → private SQLite + originals
                                   → Consultant → bounded retrieval → Hubris HTTPS
                         → download.php → session + integrity → attachment
```

Требование: **PHP >= 7.4** (для нового production предпочтительна поддерживаемая версия, совместимая с Bitrix), `mbstring`, `PDO`, **pdo_sqlite**. DOCX требует `ZipArchive`; ИИ — `curl`, доверенные CA и исходящий HTTPS к согласованному endpoint. Composer/npm зависимости отсутствуют.

SQLite выбран как изолированное хранилище пилота без изменения схемы БД портала. Наличие расширения **не предполагается**: проверяется в защищённой диагностике. Если SQLite отсутствует, приложение закрывается ошибкой, а не пишет JSON в публичную папку. Установка расширения/выбор MySQL D7-адаптера — отдельное решение администратора. Для большого корпуса, нескольких web-узлов, NFS и массовой записи нужен другой адаптер/индекс. `src/Storage.php` — граница замены; SQLite-specific schema и `changes()` тоже требуют переноса.

## Развёртывание — только после отдельного согласования

1. Системный администратор проверяет версию PHP Bitrix, расширения, права, CA, лимиты PHP `upload_max_filesize`, `post_max_size`, `memory_limit` (память с запасом для HTML 20 MiB). Уменьшите лимит загрузки при необходимости. Никакие бинарники приложение само не устанавливает.
2. Создать приватный каталог вне **всех** web-root/alias и не на общей публичной файловой системе; владелец — service account PHP, права каталога 0700, umask 0077. Хранить SQLite и originals вместе; резервные копии — консистентным snapshot/SQLite backup с оригиналами. Не размещать в `/local/apps/.../storage`.
3. Скопировать `config.example.php` вне document root, права 0600, настроить storage. Указать абсолютный путь в переменной окружения PHP-FPM `NORM_BASE_CONFIG`. Учесть `clear_env`/open_basedir. Конфигурация, токен и приватный каталог никогда не публикуются.
4. Скопировать приложение, например, в `/local/apps/norm-base/`. Web-сервер должен отдавать `.mjs` с JS MIME. Запретить прямой HTTP-доступ к `src/`, `migrations/`, `tests/`, `README.md`, `config.example.php`, dotfiles; разрешить только entrypoints и assets. Выключить `display_errors`; не логировать тела запросов/ответов и Authorization.
5. Войти администратором Bitrix, открыть `install.php`, проверить диагностику и явным POST подготовить идемпотентную схему. GET ничего не устанавливает. Миграция не удаляет данные. Для будущих миграций нужен versioned migration runner.
6. **Сначала проверить same-host core session в iframe**, внутреннего сотрудника, экстранет и админа на конкретной сборке. Не передавать роли/USER_ID/AUTH_ID из POST. Текущий код консервативно запрещает непустой `EXTERNAL_AUTH_ID` (SSO-сотрудники могут потребовать отдельной согласованной политики).
7. Регистрация локального приложения/пункта меню в Bitrix выполняется администратором отдельно. `index.php` — UI, `install.php` — диагностика/схема, **не OAuth callback**. Код не использует JS SDK/rest installation payload и не обменивает AUTH_ID. Если портал требует OAuth lifecycle установки, разработать отдельный валидируемый адаптер с секретами вне web-root; до этого OAuth установка не поддерживается. Не использовать `install.php` как якобы готовый REST install handler. Доверять только фактической core session на том же origin. CSP разрешает iframe только своего origin.
8. При включении ИИ администратор вручную задаёт **точный** OpenAI-compatible Hubris endpoint (полный URL chat completions), token и `openai/gpt-4o-mini`. URL не угадывается. Выключенный `ai_enabled` не делает запросов. Прокси получает только вопрос и максимум 6 проверенных фрагментов; доступ к нему означает передачу этих текстов внешнему LLM. Проверьте контракт JSON mode/response/model на тестовом публичном документе после разрешения расходов. Redirects запрещены, HTTPS/CA проверяются. Ошибки upstream не раскрывают токен.
9. Выполнить тесты и ручную приёмку ниже, только затем открыть сотрудникам.

## Работа с редакциями и сроки

Все интервалы **включительные** (`YYYY-MM-DD`); пустая конечная дата означает «конец не установлен», а не официальное подтверждение бессрочности. Дата проверки источника не подменяет дату принятия/редакции акта. Статус `ready` означает ручную сверку администратором, а не юридическую актуальность всей базы.

Сначала загрузить оригинал. Для новой редакции указать ID существующего документа. Сверить оригинал и заполнить JSON фрагментов, например:

```json
[{"locator":"Статья 2, пункт 1, страница 3","body":"Дословный текст из оригинала после ручной проверки.","effective_from":"2026-12-01","effective_to":null}]
```

Срок пункта должен лежать внутри срока редакции. Для разных дат вступления частей — отдельные пункты. При неизвестном начале не публиковать. Отсутствующие/непроверенные нормы не дают ИИ оснований утверждать отсутствие требования в законодательстве.

**Ограничение первого среза:** опубликованные сроки не редактируются; отдельного append-only механизма исправлений/отзыва/закрытия прежней открытой редакции пока нет. При пересечении поиск безопасно исключит обе редакции. Это блокер перехода к полноценному жизненному циклу нормативной базы; не исправлять историю прямым SQL без согласованной процедуры. Оригиналы не заменять.

## Извлечение и OCR

HTML: встроенное преобразование в plain text — только предложение для сверки. PDF всегда `ocr_needed` (не означает, что файл обязательно скан), DOC/DOCX — `pending_review`. Автоматического извлечения PDF/Word, конвертации DOC и OCR **нет**. Не запускаются shell/бинарники. Срез работает с ручной вставкой сверенных фрагментов. В дальнейшем нужны изолированные extraction/OCR workers с лимитами страниц/памяти/времени, антивирус, запись версии инструмента и provenance; воркер не должен автоматически публиковать результат.

## Существующий корпус — отдельный offline импорт, сейчас не запускается

Не копировать knowledge-base в публичную папку и не сканировать весь диск. Будущий CLI importer должен принимать явный manifest согласованных файлов, делать dry-run/лимиты, проверять расширение/сигнатуры/hash, сохранять новый оригинал и запись `pending_review`/`ocr_needed` транзакционно, сохранять официальный источник и исходные метаданные, не угадывать актуальность по имени/mtime. Дедупликация — по hash + внешнему ID, импорт идемпотентен. Работать партиями; OCR только отдельной согласованной задачей. Сам importer в этом срезе **не реализован**.

Переиспользованы идеи `norm-bot-pilot`: bounded retrieval, отделение проверенных источников, fail-closed citation verification. Текст корпуса, секреты и код бота не копировались.

## Проверка и приёмка

Без установки пакетов:
```text
node --test tests/ui.test.mjs
python -B tests/schema.py
php tests/domain.php
php -l index.php   # также остальные *.php
```

PHP-тесты включают даты, plain text, выдуманные цитаты, чужой source ID, публикацию/повторную публикацию и отсев истёкших сроков на временной SQLite. Node-тесты проверяют UI helpers и статические контракты; они **не заменяют исполнение PHP**.

Ручные интеграционные сценарии на изолированном Bitrix:
- аноним → 401; внешний/неразрешённая группа → 403; сотрудник POST upload/review/install → 403; admin без sessid → 403;
- PDF/HTML/Word проходят корректную сигнатуру; подмена `.php.pdf`, traversal имени, большой файл, DOCX без правильного контейнера отклоняются;
- HTML с script/event handler не исполняется ни в preview, ни при download; неизвестная/непроверенная редакция не скачивается сотрудником;
- две загрузки дают разные originals/hash/history; опубликованный текст не меняется;
- сроки пункта: до/в день начала/в день конца/после; пересечение редакций → нет цитат;
- Hubris выключен/timeout/невалидный JSON/выдуманная цитата → нет неподтверждённого ответа;
- XSS в названии, вопросе, quote, locator → только textContent; токен/пути отсутствуют в HTTP-ответах;
- одновременная публикация: ровно одна успешная; восстановление согласованной резервной копии.

Перед production: PHP lint/runtime + Bitrix E2E, отдельная проверка доступа SSO/extranet, аудит безопасности, антивирус загрузок, DB/поисковый адаптер для масштаба, отзыв/append-only исправление сроков, мониторинг, общая квота/конкурентность ИИ (сейчас только 15 секунд на сессию, не полноценная квота), постраничные списки/поиск, OAuth lifecycle при необходимости. Не считать этот срез промышленно завершённым.
