# Локальный пилот нормативного чат-бота Эском

Независимый Node.js backend, без npm-зависимостей, без доступа к настройкам или секретам OpenCode.
Ничего не регистрирует. Сам backend не создаёт туннель; отдельный скрипт ниже запускается только с разрешения пользователя.
По умолчанию `offline`: **никаких LLM/Bitrix API-вызовов**, даже если callback принят.
Битрикс: строго личные чаты, только сотрудники **835 и 626**; список зафиксирован в коде.
Telegram: отдельный transport; по явному запросу пример настроен на **public/private chats only**.
Без `TELEGRAM_ACCESS_MODE` код безопасно выбирает allowlist с пустым списком.

## Быстрый локальный запуск (PowerShell)

Из корня проекта:

```powershell
cd .\norm-bot-pilot
$node = "$env:LOCALAPPDATA\Programs\nodejs\node.exe"
& $node --test test/*.test.mjs
Copy-Item .env.example .env
# Если .env уже существует, НЕ перезаписывайте его.
& $node --env-file=.env src/server.mjs
```

В другом окне: `Invoke-RestMethod http://127.0.0.1:8787/health`.
Ctrl+C — остановка. Слушает только `127.0.0.1`; интернет-входов нет.
Пакеты устанавливать не нужно. На старте читается база; обновление индекса — перезапуск.
При отсутствии обязательной структуры/превышении лимита базы запуск закрыто отказывает.
`/health` показывает режим, готовность аутентификации и счётчики, без вопросов, ключей и путей.

## Telegram: отдельный локальный пилот без туннеля

`src/telegram.mjs` использует только long polling `getUpdates` к официальному Telegram Bot API.
Не запускает HTTP-сервер/туннель, не требует Bitrix scope, application_token или bot ID.
Существующий Bitrix entrypoint не изменён. Реальных Telegram вызовов при подготовке не выполнялось.

**Корпоративное использование Telegram не считается согласованным.**
Вопросы/ответы будут проходить через Telegram; вопросы и найденные фрагменты — через Hubris.
В Telegram bot chats нет сквозного шифрования Secret Chat. Ответы бота можно копировать
и пересылать: `protect_content` сознательно не используется. Не передавайте персональные данные, корпоративные секреты,
либо документы, передачу которых ваша организация не разрешила. До одобрения — только допустимые
тестовые нормативные вопросы, после отдельного разрешения запуска.

### 1. Создать отдельного тестового бота вручную

В официальном [@BotFather](https://t.me/BotFather) выполните `/newbot`, выберите название
и уникальный username, оканчивающийся на `bot`. Сохраните новый токен **только локально**
в существующем `.env`: `TELEGRAM_BOT_TOKEN=...`. Не присылайте токен/скриншот в чат.
При утечке отзовите токен в BotFather. Для пилота не включайте inline, группы или paid broadcasts.
Нужен отдельный новый бот без webhook и других потребителей updates.

Не перезаписывайте `.env` примером и не меняйте существующие секреты.
Для текущего публичного пилота добавьте `TELEGRAM_ACCESS_MODE=public`; `RUN_MODE=offline` сохранить.
В public доступны все люди в **личных чатах**, Telegram IDs собирать не обязательно.
Username бота не является контролем доступа: даже если ссылку дадите двум-трём людям,
бот технически общедоступен. Группы/каналы по-прежнему отвергаются.
Для закрытого варианта установите `TELEGRAM_ACCESS_MODE=allowlist` и вручную заполните
`TELEGRAM_ALLOWED_USER_IDS`. Без переменной режим allowlist; пустой список = **deny all**.
Автоматической регистрации по `/start` нет.
Bitrix IDs **835/626 нельзя копировать сюда**: конфигурация их отклоняет.

### 2. Получить свой Telegram ID без сторонних ботов (нужно только для allowlist)

Откройте **личный** чат с созданным ботом и отправьте ровно `/start` (за последние 5 минут).
Только после отдельного разрешения bootstrap выполните локально:

```powershell
& $node --env-file=.env src/telegram.mjs --bootstrap --allow-telegram-bootstrap
```

Команда делает `getMe` и **один** `getUpdates` (ожидание до 25 секунд), не обращается к LLM,
ничего не отправляет в Telegram и не подтверждает updates через offset.
В stdout выводятся **только numeric `from.id`** свежих `/start` из private-чата:
без имён, username, текстов, токенов или raw ошибок. Если подходящих событий нет — stdout пустой;
отправьте новый `/start` и отдельно разрешите повтор. Другие события временно принимаются
Bot API в память и отбрасываются: API не умеет серверно фильтровать updates по тексту `/start`.
Не запускайте bootstrap одновременно с polling/другой интеграцией этого бота.

Bootstrap **не доказывает**, кому принадлежит ID, и не добавляет его в allowlist.
Не публикуйте нового бота до настройки; организуйте `/start` участников по одному,
подтвердите принадлежность ID через доверенный канал. Не разрешайте незнакомые ID из выдачи.
Владелец вручную записывает подтверждённые Telegram IDs через запятую
в `TELEGRAM_ALLOWED_USER_IDS`. Максимум 10 пользователей для пилота.

### 3. Запускать ответы только после явного разрешения

Проверьте локально `LLM_MODEL=dots-studio/dots-3-note-preview:free`, `LLM_MAX_TOKENS=1400` (или меньше),
правильные Hubris endpoint/отдельный ключ. Telegram entrypoint ограничивает эту бесплатную модель/endpoint,
не использует Bitrix-реквизиты и не выбирает провайдера автоматически.
Без токена/allowlist/LLM настроек live-запуск закрыто отказывает **до сети**.

```powershell
# Без флагов и с RUN_MODE=offline: только сообщение offline, никаких API-вызовов.
& $node --env-file=.env src/telegram.mjs
# ТОЛЬКО после подтверждения отправок/расходов: live лишь внутри этого процесса.
& $node --env-file=.env src/telegram.mjs --live --allow-telegram-polling --allow-paid-llm
```

`--allow-telegram-polling` — явное согласие запуска с отправкой ответов;
`--allow-paid-llm` — отдельное согласие платных вызовов Hubris только по входящим вопросам.
Не переключайте общий `RUN_MODE` ради Telegram: `--live` переопределяет его только в памяти
этого entrypoint, `.env` и Битрикс не затрагиваются. Ctrl+C прекращает polling;
незавершённый LLM-вызов может завершаться до своего таймаута, после остановки отправка подавляется.

Допущенный `/start` получает приветствие/предупреждение о данных без вызова LLM
(в public допущен любой человек в private-чате).
Далее используется тот же retrieval, source grounding, восстановление оригинальных цитат
и короткая пометка «Справочно.»; краткая оговорка про сверку с юристом есть в `/start`. Тон — профессиональный, но дружелюбный: «в сборке указано…», без самоуничижения
и категоричных юридических выводов. Выводы модели без дословной цитаты отбрасываются;
если точных цитат не осталось, показывается вежливый отказ с подсказкой уточнить акт/статью.
Для уточняющих вопросов worker хранит в оперативной памяти только номер последнего явно
названного федерального закона и статью: отдельно для каждого чата, не более 30 минут,
без записи вопросов и ответов на диск. `/reset` очищает этот контекст, `/start` начинает его заново.
Общие юридические термины сначала проверяются по встроенному глоссарию. Короткие запросы
вида «что такое…» при отсутствии материалов в сборнике могут получить отдельную общую
консультацию модели с явной пометкой «вне локального сборника». Этот режим не заявляет
о поиске в интернете и не используется для неподтверждённых актуальных норм, дат или статусов.
Если локальный поиск не дал источников либо пользователь явно просит проверить актуальность,
Telegram-worker обращается к документированному API `publication.pravo.gov.ru/api/Documents`.
Запрос выполняется только к фиксированному официальному HTTPS-хосту, без редиректов, с лимитами
10 секунд и 512 КБ. Результат подтверждает реквизиты и факт официального опубликования, но
не объявляется доказательством текущего статуса или консолидированной редакции. Неподтверждённые
поисковые интерфейсы ЕАЭС, Росздравнадзора, Минздрава и Минпромторга не используются.
Если модель не смогла сформировать ответ с проверяемой точной цитатой, Telegram-worker не
повторяет запрос и не ослабляет проверку цитат. Вместо отказа он может дать отдельно помеченную
общую консультацию фармюриста без номеров статей, дат, ссылок и заявления об актуальности.
Production-worker использует одну недорогую модель Hubris `openai/gpt-4o-mini` с бюджетом
не более 1400 выходных токенов. По каталогу Hubris на 23.11.2026 её тариф составлял
18,94 ₽ за 1 млн входных и 75,75 ₽ за 1 млн выходных токенов. Цены могут меняться.
Автоматического fallback на другую, в том числе более дорогую, модель нет.
Неавторизованные сообщения игнорируются **без ответа и без LLM**.
Принимаются только новые `message` с private chat ID = numeric `from.id`, человек,
не via-bot и не старше 5 минут. Пересланные сообщения принимаются: отправитель запроса — тот,
кто переслал, а исходное содержимое считается непроверенными данными. Группы, inline, каналы, бизнес-сообщения,
edited updates, документы, фото/голос и запросы длиннее 2000 символов отбрасываются.
Никакой загрузки вложений или чужой истории нет.

По последнему запросу пользователя **дневных/per-user/session квот, лимита числа платных вызовов
или программного рублёвого бюджета для Telegram нет**. Persistent budget-счётчик не используется.
Старые 5 запросов/мин и 50 сообщений/запуск отключены только в Telegram; в Битрикс сохранены.
Polling работает до Ctrl+C/ошибки, без ограничения числа циклов или срока сессии.
Оставлены только технические защиты: последовательная очередь максимум 20 активных/ожидающих
заданий, ограниченный дедуп-кеш (1000 ID, TTL 10 минут), таймауты и размеры сообщений.
При заполнении очереди/кеша лишние сообщения могут быть отброшены, это защита памяти,
не дневная/денежная квота.
Один plain-text ответ максимум 4096 символов, без parse_mode, превью ссылок и paid broadcasts;
при превышении — просьба сузить вопрос вместо обрезанной цитаты. Obsidian-ссылки локальные,
Telegram-клиент может не сделать их кликабельными.
Bot API timeout 40 сек, long poll 25 сек, LLM 45 сек, ответ API до 512 KiB.
URL Telegram **содержит секретный токен**: raw ошибки, headers, URLs/updates не логируются.
Нет автоматических повторных отправок/платного fallback. Ошибка API/конфликт webhook/poller
останавливает polling; webhook автоматически не удаляется.

**Публичный бот без квот может привести к неожиданным расходам**, в том числе из-за чужих
пользователей. Небольшое планируемое число участников не гарантирует небольшой счёт.
Финансовый предел задайте отдельно в кабинете провайдера API. Ограничение числа запросов
в любом случае не было бы гарантией рублёвого бюджета; здесь не задаётся и оно.
`LLM_MAX_TOKENS` ограничивает размер одного ответа (техническая настройка), не общие расходы.

В public-ответах нет локальных путей, имён служебных файлов и Obsidian URL: только
название акта/раздел, проверенная непрерывная цитата, дисклеймер и до двух официальных
ссылок из найденных источников. URL проверяются синтаксически и по точному official host,
но не открываются автоматически; доступность/соответствие публикации требует проверки.
Полные документы/вложения не отправляются. Если модель пытается включить локальный путь,
ответ отклоняется. Внутренние Bitrix и allowlist-ответы сохраняют прежний формат источников.

Offset/dedup/очередь хранятся в памяти. Следующий `getUpdates` подтверждает ранее
отброшенные/принятые в очередь updates, **не успешную доставку**; при перегрузке сообщения
могут быть отброшены, при перезапуске возможны потери/повторы. Это локальный пилот, не production.

Telegram туннель не нужен. Если прежний Bitrix quick tunnel ещё работает, рекомендуем
остановить его через `scripts/stop-tunnel.ps1`, когда Bitrix-тест больше не нужен;
автоматически на этом этапе он не останавливался.

### Контролируемый background запуск @zakfarm26_bot

После явного разрешения пользователя запускается отдельный worker:

```powershell
& $node scripts/telegram-worker.mjs --prepare --live --allow-telegram-polling --allow-paid-llm
```

Worker читает ключи только внутри Node через `--env-file=.env`, проверяет `getMe.username`
строго `zakfarm26_bot`, затем `getWebhookInfo`. Если URL webhook непустой — останавливается,
не вызывает `deleteWebhook`; сначала согласуйте с владельцем другой интеграции.
До этих проверок `getUpdates`/отправок нет. Успех запуска означает проверку Telegram и
готовность polling, **не новый успешный тест нормативного ответа/LLM**.
Ровно один owned worker охраняется `.state/telegram-worker.lock`; существующий чужой процесс
не завершается. При нештатном завершении оставшийся lock закрыто блокирует новый запуск.
Модель переопределяется только в памяти на `dots-studio/dots-3-note-preview:free`, размер ответа 1400;
общий RUN_MODE остаётся offline, Bitrix live не включается. В .env ничего не переписывается.
`.state/telegram-worker.json`/`telegram-safe.log` содержат только PID, статус и безопасные коды,
не token-bearing URL, вопросы или персональные данные.

Остановка только проверенного owned worker:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/stop-telegram.ps1
```

После запуска пользователь сам открывает `https://t.me/zakfarm26_bot` и отправляет `/start`.
Приветствие проактивно не отправляется; LLM не вызывается без входящего нормативного вопроса.

Официальная документация:
[BotFather](https://core.telegram.org/bots/features#botfather),
[getUpdates](https://core.telegram.org/bots/api/methods/getupdates.md),
[getMe](https://core.telegram.org/bots/api/methods/getme.md),
[sendMessage](https://core.telegram.org/bots/api/methods/sendmessage.md).

## Что настраивать только локально

Создайте `.env` из примера и заполните в локальном редакторе (`notepad .env`).
**Не присылайте содержимое файла, ключи, webhook URL, скриншоты токенов в чат.**
Не вводите секреты в аргументах PowerShell: они остаются в истории. Файл исключён из git
локальным `.gitignore`, но не зашифрован: ограничьте NTFS-доступ своей учётной записью,
не храните копии в общей/облачной папке, не запускайте сервис под общей учётной записью.
Пример ограничения ACL после создания файла (проверьте корпоративные требования резервного копирования):

```powershell
$me = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
icacls .env /inheritance:r /grant:r "${me}:(R,W)"
```

Нужно заполнить:

| Поле | Откуда |
|---|---|
| `BITRIX_MEMBER_ID` | Доверенная настройка/установка приложения для конкретного портала |
| `BITRIX_APPLICATION_TOKEN` | Токен проверки событий данного приложения/интеграции, полученный доверенным способом |
| `BITRIX_BOT_ID` | После отдельно согласованной регистрации legacy-бота |
| `BITRIX_WEBHOOK_URL` | **Новый** входящий вебхук портала с `imbot`, после отзыва показанного на скриншоте |
| `BITRIX_CLIENT_ID` | Тот же идентификатор владельца бота, что использован в `imbot.register` |
| `LLM_PROTOCOL` | Строго `openai-chat-completions` |
| `LLM_PROVIDER` | Явно выбранный пользователем провайдер (название для учёта) |
| `LLM_ENDPOINT` | Полный HTTPS URL Chat Completions API этого провайдера, без ключа в URL |
| `LLM_MODEL` | Точное имя модели у выбранного провайдера |
| `LLM_MAX_TOKENS` | Явный бюджет выходных токенов, 256–8192; без поля — 1400 |
| `LLM_API_KEY` | **Отдельный** выданный пользователем ключ, не секреты OpenCode |

Нужна поддержка `messages`, `max_tokens`, `response_format: json_object` и ответа `choices[0].message.content`.
Это не универсальный SDK для всех провайдеров; несовместимый API требует отдельного адаптера.
Проверьте условия хранения данных у провайдера и выставьте денежный лимит отдельному ключу.
У приложения нет механизма доступа к OpenCode auth/config. Не копируйте оттуда OAuth-токены.

### Предварительная конфигурация Hubris

В `.env.example` выбран Hubris с Base URL `https://api.hubris.pw/v1`.
Адаптер **не дописывает** `/chat/completions`, а отправляет запрос прямо в `LLM_ENDPOINT`,
поэтому настройка — **`https://api.hubris.pw/v1/chat/completions`**, не один Base URL.
По явному запросу пользователя для Telegram-бота выбрана **бесплатная** модель
**`dots-studio/dots-3-note-preview:free`**, бюджет **1400** выходных токенов.
Fallback на платные или другие модели отключён: worker и валидация требуют ровно эту модель
и endpoint `https://api.hubris.pw/v1/chat/completions`.

**История проверок free-модели:** ранний тест с бюджетом 1400 давал `finish_reason=length`
и пустой `content`; после исправления валидации (неточные выводы модели отбрасываются, а не
аннулируют весь ответ) тот же вопрос «Что говорит 331-ФЗ про сроки вступления?» дал
`reason=grounded`: две дословные цитаты, источник, официальные ссылки и дисклеймер.
Reasoning не используется вместо ответа. Повторов с увеличенным бюджетом и fallback нет.

Для нового **отдельно разрешённого** единичного free-теста есть
`scripts/free-smoke.mjs`: запускается вручную с `node --env-file=.env scripts/free-smoke.mjs --allow-one-free-request`.
Скрипт допускает только указанные Hubris endpoint/free-model, требует исходный `RUN_MODE=offline`,
не вызывает Битрикс и не меняет `.env`. Не запускать повторно автоматически.
Выводит статус HTTP и безопасные причины валидации, а не headers, сырой ответ или reasoning.

Универсальный `scripts/smoke.mjs` поддерживает **один** запрос с отдельным флагом
согласия `--allow-one-free-request` либо `--allow-one-paid-request`.
Выбор модели можно явно переопределить `--model=...` только в памяти процесса,
выходной бюджет — `--max-tokens=...` (256–1400), не меняя `.env`.
Требует исходный offline и фиксированный Hubris HTTPS endpoint; без согласия не обращается в сеть.
Не запускайте команду повторно без отдельного разрешения расходов:

```powershell
& $node --env-file=.env scripts/smoke.mjs --allow-one-free-request --model=dots-studio/dots-3-note-preview:free --max-tokens=1400
```

**Результат разрешённого mini-теста:** один запрос, HTTP 200, `finish_reason=stop`,
ответ получен, но сервер отклонил его: `quote_whitespace_mismatch` (цитата отличается
пробельными символами). **Функциональный успех не подтверждён**; в Битрикс ничего не отправлялось.
Usage: 3115 входных + 201 выходных = 3316 токенов, не сумма денег.
Проверка точности цитат не ослаблялась, автоматического повтора не было.

**Автоматического fallback нет:** на запрос используется ровно настроенная модель;
при ошибке не происходит повторного выбора, переключения на другую или платную модель.
Это гарантия клиентского кода, не политики маршрутизации самого провайдера.
Поведение провайдера и бесплатность необходимо проверить отдельно.

Раскрытый на скриншоте API-ключ необходимо **отозвать**. Новый отдельный ключ введите
только локально в `.env` описанным выше способом. Не используйте раскрытый ключ.
В примере ключ пустой, `RUN_MODE=offline` сохранён; реальный `.env` автоматически не создаётся.

`RUN_MODE=live` разрешает оба внешних вызова и требует все настройки; включать
**только после отдельного согласования первого сообщения и расходов на LLM**.
Сейчас оставить `offline`. Само наличие ключа не включает live.

## Блокирующий шаг: доверенная аутентификация формы Битрикс

Показанная форма «Информировать сотрудников в чате» ещё не доказывает, что
выданы все необходимые параметры безопасной callback-интеграции.
Официальный legacy `ONIMBOTMESSAGEADD` содержит `auth.application_token`,
`auth.member_id`, `auth.domain`, `data.BOT[bot_id].BOT_ID`, `data.PARAMS` и `data.USER`.
Обработчик сверяет токен в constant-time с **заранее доверенным** значением,
member_id, портал, получателя-бота, отправителя/автора/диалог и тип личного чата.
Incoming OAuth access/refresh tokens и endpoint-адреса никогда не используются.
При отсутствии любого необходимого поля запрос отклоняется.

**Нет автоматического обучения токену из первого входящего запроса (TOFU).**
Нельзя просто принять неизвестный токен из публичного callback, даже если ID отправителя — 835.
Сначала администратор должен подтвердить способ получения токена и принадлежность бота.
Если форма не показывает доверенный токен событий, нужен отдельный контролируемый шаг
настройки/установки локального приложения с получением токена по доверенному каналу,
либо другой документированный безопасный механизм после проверки фактической версии коробки.
Пилот не реализует OAuth-установку и не заменяет её неподтверждённым первым событием.
`CLIENT_ID` — идентификатор владельца legacy-бота, **не** `application_token`; webhook тоже не заменяет токен события.
Если реальный payload формы отличается от официального, не ослабляйте проверки: сначала
сравните названия полей локально, без вывода токенов/текста вопросов в журналы.

## Callback и доставка ответа

- `POST /bitrix/events`: JSON или стандартная PHP bracket form-urlencoded.
- Только `ONIMBOTMESSAGEADD`; приветствия, обновления и остальные события сейчас получают 403.
- Размер тела 64 KiB, вопрос до 2000 символов; событие не старше/не дальше будущего 5 минут.
- `200 accepted/duplicate` сразу после проверки и постановки в очередь, **не текст ответа**.
- Неверная аутентификация: 401; запрет чата/пользователя: 403; перегрузка: 429.
- Последовательная очередь максимум 20, 5 запросов/мин на пользователя, 50 принятых заданий
  за запуск процесса (включая offline); дедупликация 10 минут по bot/message ID.
- LLM timeout 45 секунд; отправка Битрикс 15 секунд; исходящие редиректы запрещены,
  ответ API ограничен 128 KiB; автоматических повторных отправок нет.
- Ошибки задания — только счётчик и код `job_failed`, без текста исключения/вопроса/URL.
- Отправка: POST строго на настроенный портал, `imbot.message.add.json`,
  поля `BOT_ID`, `CLIENT_ID`, `DIALOG_ID`, `MESSAGE`, `URL_PREVIEW=N`, `SKIP_CONNECTOR=Y`.
  Адресат повторно проверяется по фиксированному allowlist.

Дальнейший HTTPS reverse proxy/туннель должен проксировать **только**
`POST /bitrix/events`, не `/health`; сертификат валидный, без request/body/debug logging,
с лимитами запросов на периметре. Регистрация бота не выполнялась.
Для коробки могут потребоваться сетевые доступы к очереди Битрикс, не только от сервера портала.
Выбранная в интерфейсе опция «ответы поступают сразу» должна быть проверена отдельно:
данный backend всегда отправляет ответ отдельным REST-вызовом, не синхронным телом callback.

### Временный HTTPS-туннель (только разрешённый тест)

Установлен user-space бинарник `%LOCALAPPDATA%\Programs\cloudflared\cloudflared.exe`,
версия 2026.11.1 из официального [релиза Cloudflare](https://github.com/cloudflare/cloudflared/releases/tag/2026.11.1).
SHA256 проверен по опубликованному хешу:
`341deda3db5ec498a0482254d6c38c0b7cf01a30c37bb5dd95d2216d08955e35`.
PATH, firewall, службы, настройки администратора не меняются.
[Официальная документация Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).

`node scripts/tunnel.mjs --prepare` запускает отдельный background worker и cloudflared.
Worker загружает `.env` только внутри Node-процесса, **принудительно offline/8787**,
не передаёт ключи LLM/Bitrix в cloudflared. Слушает только `127.0.0.1:8787`.
Если порт занят другим процессом — закрыто отказывает и не туннелирует чужой сервис.
В этом режиме отключён даже `/health`: публично разрешён только `POST /bitrix/events`,
остальные пути/методы возвращают 404. Файлы, vault, инструменты OpenCode не публикуются.
Обычный standalone server по-прежнему имеет безопасный локальный `/health`.

Готовность фиксируется по событию регистрации tunnel connection, без polling.
`.state/tunnel.json` содержит только временный публичный origin/callback, PID и флаги состояния.
`.state/tunnel-safe.log` — только безопасные сообщения worker, без сырых заголовков/вопросов/
cloudflared debug-логов. Время жизни автоматически ограничено **двумя часами**.
Сырой вывод cloudflared не сохраняется, автoобновление выключено, metrics только на loopback.
Cloudflare завершает TLS и технически может обрабатывать трафик: не отправляйте туда секреты/документы,
пока не согласован реальный тест. Это сторонняя тестовая инфраструктура без SLA.

Остановка (из папки `norm-bot-pilot`):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/stop-tunnel.ps1
```

Скрипт сверяет PID и командную строку worker перед остановкой его дерева процессов.
После остановки статус-файл может быть устаревшим; URL исчезает, при следующем запуске он другой.
Не перезапускайте туннель автоматически.

**Наличие HTTPS URL не решает bootstrap.** Если нет заранее доверенных `application_token`,
`member_id` и bot ID, callback остаётся закрытым (401) и не выдаёт нормативный ответ.
Не вводите тестовый URL в форму как «готового бота». Сначала администратор подтверждает
доверенное получение параметров legacy-интеграции/локального приложения.
Secret callback path для отдельного контролируемого handshake — лишь возможный проектный вариант,
сейчас **не реализован**; обычный публичный путь не является доказательством подлинности.
Нельзя отключать token-проверку или учиться токену первого публичного запроса ради регистрации.

## Поиск, источники и безопасность

Разрешённый корень зафиксирован: `C:\Users\saruchevaad\Desktop\Эском\База знаний\Нормативные документы_2026-11-18`.
HTTP не принимает пути, имена файлов или адреса для скачивания.
Сканируются только `Законы`, `Постановления`, `Приказы`, `ЕАЭС`, `Изменяющие акты`,
`Будущие нормы`, `Архив`; только `.md/.html/.htm`, без скрытых каталогов/симлинков/junction.
Проверяются canonical paths; изменять содержимое базы во время запуска не следует.
Это не защита от локального администратора или атакующего с правом менять саму базу.
JSON/DOCX/PDF/XLSX и служебные каталоги не читаются.
Ограничения: 12 MiB на файл, 128 MiB суммарно, 5000 файлов, 150000 фрагментов.
Файлы >12 MiB пропускаются: поиск не гарантирует полноту сбора.

Текст HTML извлекается упрощённо, без исполнения HTML/JS и загрузки ресурсов.
Лексический поиск без embeddings/морфологии: максимум 4 фрагмента по 1800 символов.
Наружу отправляются **только вопрос и эти фрагменты с относительными именами**, не весь vault,
не данные сотрудников и не предыдущие диалоги. Без источников LLM вообще не вызывается.
Нет достоверной релевантности — честный отказ; возможны ложные отказы/совпадения.

Для запросов с номером **ФЗ/ФКЗ** поиск сначала устанавливает точный номер и тип акта
(включая варианты Unicode-дефиса), затем ограничивается собственной папкой акта.
Упоминания поправок в других законах не заменяют сам акт; отсутствующий/неоднозначный
номер приводит к отказу, а не выбору «похожего» закона.
В вопросах о вступлении в силу приоритетны карточка с ограничениями полноты и фрагмент
полного текста с общей нормой/исключениями. Даты не зашиты в алгоритм.
Для других видов актов пока действует простой текстовый поиск; морфология и сложные
междокументные вопросы полноценно не поддерживаются.

Модель получает отдельные системные правила; документы/вопрос сериализованы как недоверенные данные,
инструментов/доступа к файлам у модели нет. Каждый вывод должен вернуть существующий ID источника
и непрерывную точную цитату 40–500 символов; сервер проверяет цитату, генерирует ссылки сам,
не доверяет модельным URL/BB-разметке и добавляет обязательный дисклеймер.
Это снижает риск prompt injection, **но не доказывает корректность интерпретации или иммунитет модели**.
Нет автоматической юридической верификации связи вывода и цитаты.
Для юридически значимых решений нужна проверка специалистом.

`inspectAnswer` различает пустой content, JSON/fences, отказ модели, чужой источник,
цитату короче 40/длиннее 500 символов и неточную цитату.
Теперь допустима только канонизация последовательностей Unicode **White_Space** в один пробел:
обычные/неразрывные пробелы, табуляции, переносы. Поиск остаётся непрерывным и регистрозависимым:
буквы, цифры, пунктуация, порядок слов не изменяются; удалять слова/склеивать раздельные
фрагменты нельзя. NUL, zero-width символы, BOM, soft hyphen не игнорируются.
Индексная карта UTF-16 восстанавливает **оригинальный непрерывный диапазон источника**;
в цитате ответа выводится он, не изменённый моделью текст.
Лимит входной цитаты 40–500 символов; после свёртки whitespace минимум также 40.
Восстановленный диапазон ограничен 1000 символами (иначе отказ, без обрезки).
Цитаты с BB/HTML-разметкой или HTTP/Obsidian URL закрыто отклоняются, а не переписываются
под видом дословной цитаты. Это ограничение безопасного отображения текущего пилота.
Канонизация протестирована **только offline**. Сырой ответ предыдущего live-теста
не сохранялся; считать его прошедшим после правки нельзя, live-успех не подтверждён.
Fenced JSON/произвольный текст не «выковыриваются», reasoning не подменяет content,
`finish_reason=length` всегда приводит к отказу.
Диагностика по умолчанию не логируется; вызывающий может получить только безопасные коды/флаги.
Отказ пользователю больше не утверждает, что документ обязательно отсутствует в базе.

Источники — относительное имя файла, строки **извлечённого текста**, `obsidian://open`.
У получателя должны быть Obsidian и тот же vault; HTML может открываться неудобно/не поддерживаться
как заметка. Это локальные ссылки, не публикация документов на Диске или в интернете.
Статус/редакция не проверяются по интернету. Наличие файла в «Архив»/«Будущие нормы»
не означает действующую норму; это явно указано модели и в ограничениях ответа.

## Ограничения пилота и тесты

Очередь и дедуп только в памяти: при остановке задания теряются, после перезапуска
возможны повторные события в 5-минутном окне. Показатели и лимит 50 сбрасываются.
ACK не означает успешной доставки; сбой upstream увеличивает `failed`, сообщение не повторяется.
Для промышленного режима нужны durable queue/outbox, контроль доставки, обработка обновлений,
тест с реальным payload/токеном и проверка качества на нормативных вопросах.
Нельзя обещать exactly-once доставку.

Тесты: unit авторизации, allowlist, личные чаты, таймстамп, parser, дедуп/лимиты,
поиск/цитаты/недоверенные данные; HTTP-интеграция на loopback; mock-контракты LLM/Bitrix.
Ни один тест не обращается к внешнему LLM или реальному Битрикс.
Тест prompt injection проверяет границы данных и отсутствие инструментов, не поведение настоящей модели.
